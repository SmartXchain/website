// 02 — ARCHITECTURE

One static build, served from 300+ edge cities.

Every part of the site is built ahead of time — homepage, category pages, every post, the search index, even the RSS feed and sitemap. Cloudflare Pages stores the output, replicates it to Cloudflare's edge network, and serves it from the closest data center to each reader. There's no server you maintain.

What this gets you

  • No servers to babysit. Cloudflare Pages handles build, hosting, and SSL automatically.
  • Free CDN globally. Pages serves from the same edge network as Cloudflare's enterprise customers.
  • Preview deploys on every PR. You can review changes on a live URL before merging to main.
  • Rollback in one click. Every deploy is preserved; revert from the Pages dashboard.
  • Performance budget basically solved. Static HTML + edge caching = sub-200ms TTFB anywhere.
// 03 — TECH STACK

Boring tech, in the best way.

Every choice below is optimized for: solo author velocity, low cost, and the lowest possible number of moving parts.

// Framework

Astro

Static site generator built for content sites. Ships zero JS by default. First-class MDX support. Battle-tested on Cloudflare Pages. Better Lighthouse scores than Next.js for this use case.

// Styling

Tailwind CSS

Utility-first CSS. Keeps stylesheet under 10KB after purge. Easy to maintain the Frontier dark theme as design tokens.

// Content

MDX in Git

Markdown + React/Astro components. Means charts, callouts, and tickers can be embedded directly inside an article. No CMS lock-in.

// Search

Pagefind

Static search index built at deploy time, queried entirely in the browser. Zero server cost. Works perfectly with archives.

// Newsletter

Buttondown

Indie-built, generous free tier (100 subs), great deliverability, simple API. Beehiiv is a strong alternative if you want their growth tools.

// Analytics

Cloudflare Web Analytics

Privacy-friendly, cookie-less, free, native. No GDPR banner needed.

// Why not Next.js / WordPress / Substack?

Next.js on Cloudflare is doable but adds complexity (SSR, middleware) we don't need for a content site. WordPress requires a server, a database, and constant patching. Substack doesn't own the domain experience — you'd be a tenant, not an owner.

// 04 — STORAGE

Do you need a database?

// SHORT ANSWER

No — not for v1. Every piece of content lives as a Markdown file in your Git repo and gets baked into static HTML at build time. Archives, categories, tags, search — all derived from those files.

Long answer: where each kind of data lives

DataWhere it livesWhy
Articles Markdown files in Git: src/content/posts/*.mdx Version-controlled, diffable, no DB to back up, full ownership
Categories & tags Frontmatter on each post Derived at build time into category/tag pages
Author bios Markdown: src/content/authors/*.md Reusable across posts via slug reference
Archive index Generated at build time from posts collection Just an HTML page; pagination handled by Astro
Search index Built by Pagefind at deploy time, shipped as static JSON chunks Searched in-browser, zero server cost
Live ticker (BTC/ETH/etc.) Fetched client-side from CoinGecko's free API No need to store; refresh every 60s in browser
Newsletter subscribers Buttondown's database (or your provider) You don't want to handle compliance + deliverability yourself
Analytics Cloudflare Web Analytics Aggregated, privacy-friendly, free

When you'd actually need a database

If/when any of these become priorities, we add Cloudflare D1 (SQLite at the edge — free tier covers 5M reads/month):

  • User accounts for paid/gated content
  • Comments you want to host yourself (otherwise use Cusdis or Giscus)
  • Saved articles / bookmarks per reader
  • Tip jar / paywall with subscription state
// RECOMMENDATION

Ship v1 with no database. Re-evaluate after you have 1,000 newsletter subscribers and know which "paid" features people actually want. Premature databases are how solo media projects die.

Typed schema (Astro content collections)

// src/content/config.ts
import { defineCollection, z } from 'astro:content';

const posts = defineCollection({
  type: 'content',
  schema: ({ image }) => z.object({
    title:     z.string().max(120),
    slug:      z.string(),
    date:      z.date(),
    updatedAt: z.date().optional(),
    author:    z.string(),  // references authors collection
    category:  z.enum(['chain-watch','ai-lab','deep-tech','markets','research','opinion']),
    tags:      z.array(z.string()).default([]),
    excerpt:   z.string().max(280),
    hero:      image().optional(),
    featured:  z.boolean().default(false),
    draft:     z.boolean().default(false),
  }),
});

export const collections = { posts };

// 07 — ARCHIVE

The archive, as you asked for it.

You specifically called out wanting archives. Here's exactly how that works:

// LAYOUT

Reverse-chronological list of every article ever published. 20 per page. Each row shows: date, category, headline, author, read time. Compact, dense, Bloomberg-feel.

// FILTERS

Filter chips at top: All · Chain Watch · AI Lab · Deep Tech · Markets · Research · Opinion. Separate year filter (2026, 2027, ...). Filters update URL so links are shareable.

// SEARCH

Full-text search powered by Pagefind. Built at deploy time, runs in the browser. Returns results in <50ms even for 10K+ posts. No server, no cost.

// PAGINATION

Astro generates a static page for each batch: /archive/1, /archive/2, etc. Good for SEO. Optional progressive enhancement to infinite-scroll later.

// SCALABILITY

At 1 post/day for 10 years = 3,650 posts. That's roughly 6MB of HTML and a 2MB search index. Cloudflare Pages free tier handles this without breaking a sweat. We're a long way from needing pagination strategies.

// 08 — DNS — ROUTE 53 → CLOUDFLARE

Three options. Here's the right one.

Your domain is registered at AWS Route 53 and you want hosting on Cloudflare. There are three ways to wire that up:

// OPTION A

Keep R53 nameservers, point records at Pages

Add CNAME/A records in Route 53 that target Cloudflare Pages. Works, but you lose Cloudflare's DNS, proxying, WAF, and apex-domain handling gets clunky.

Not recommended.

// OPTION B — RECOMMENDED

Move nameservers to Cloudflare, keep registrar at AWS

Domain stays registered/renewed at AWS. DNS is managed by Cloudflare. You get the full Cloudflare stack (DNS, WAF, Workers, R2, analytics) for free. Zero ongoing cost beyond the AWS renewal.

What we'll do.

// OPTION C

Transfer registrar to Cloudflare

Cloudflare offers at-cost registrar pricing (~$10/yr for .com vs ~$15 at AWS). Saves a few dollars a year. Optional, can do later, requires a 60-day wait after initial registration.

Defer until renewal.

Option B — the exact steps

  1. Sign up for a free Cloudflare account at cloudflare.com
  2. Click Add a Site → enter smartxchain.com → choose the Free plan
  3. Cloudflare auto-scans existing DNS records from Route 53. Review them, keep what you want, delete the rest. (You probably have nothing other than what Route 53 added by default — safe to clear.)
  4. Cloudflare gives you two nameservers, e.g. elliot.ns.cloudflare.com and tina.ns.cloudflare.com.
  5. In AWS Console → Route 53 → Registered domains → smartxchain.com → Edit name servers → replace AWS's four nameservers with Cloudflare's two.
  6. Wait. Propagation typically takes 1–4 hours, max 24h. Cloudflare emails you when it's active.
  7. Once active, delete the (now-unused) Route 53 Hosted Zone for smartxchain.com to stop the ~$0.50/month charge.

Then hooking up the site

  1. In Cloudflare Pages, connect to the GitHub repo. First deploy goes to smartxchain.pages.dev.
  2. In Pages → Custom domains → add smartxchain.com and www.smartxchain.com.
  3. Cloudflare auto-creates the DNS records (CNAME flattening on the apex). SSL is automatic.
  4. Set up a redirect rule: www → apex (or the inverse — your call; apex is more common now).
// SAFETY NOTE

Before changing nameservers, make a list of any current DNS records on Route 53 (especially any email MX records). If @smartxchain.com email is forwarding somewhere — like the address that received your account confirmation — those MX records need to be recreated in Cloudflare DNS, or email will stop working at cutover.

Public has marketing value (builds reputation, attracts contributors). Private is just simpler. Either works on Cloudflare Pages free tier. My default: private until launch, then make public if you're comfortable.
